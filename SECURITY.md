# Security model

Orbit 0.1.0 is a development preview. Automated tests cover specific properties; they do not establish that this application is secure enough for every unattended deployment. No independent security audit has been completed.

## Trust boundaries

1. **Network:** normal remote listening is bound to a Tailscale IPv4 address discovered from the local installed Tailscale CLI. Incoming source identity is checked through `tailscale whois --json`, cached briefly. Tailscale unavailability fails closed. No all-interface listener, public relay, Funnel, or router port mapping is configured.
   **What the Tailscale check proves:** it proves that a request comes from *some* node your tailnet lets reach this computer. It does not identify a user or a particular device. Any such node can reach the pairing endpoint: your other devices, nodes shared into your tailnet from another tailnet, and LAN devices behind a subnet router, which appear as the router's Tailscale address. An invitation is therefore the only thing standing between those nodes and a pairing: keep invitations private, and restrict reachability with Tailscale ACLs if other people's nodes can reach this computer.
   **Link policy:** remote TLS must be TLS 1.3, or TLS 1.2 with ECDHE + AES-GCM/ChaCha20-Poly1305. The viewer offers only those suites and re-checks the negotiated suite after each handshake. The host drops any other connection after the handshake and before HTTP parsing, because platform TLS stacks such as Schannel would otherwise accept CBC and static-RSA suites. See [ENCRYPTION.md](docs/ENCRYPTION.md).
2. **Application identity:** every host has a generated RSA certificate with client/server authentication use. Pairing uses a cryptographically random five-minute single-use invitation. The viewer pins the full SHA-256 certificate fingerprint before transmitting HTTP request bytes. Remote requests present a client certificate; the actual TLS certificate must match a current pairing record. Claimed device IDs do not authorize access.
3. **Authorization:** view, input, clipboard, files, and power are separate grants. Input and power require additional relevant permissions. The clipboard grant covers both reading and writing the clipboard; it does not require Control.
   **Control is full keyboard and mouse control.** A device with the Control grant can do anything the signed-in user can do through the desktop, including locking the computer (for example Win+L) or restarting and shutting it down through the normal Windows, macOS or Linux UI. It can do this even without the Power grant and even when remote power is turned off on the host. The Power grant and the host's remote-power setting govern only Orbit's dedicated lock and restart actions. Grant Control only to devices you would let use this computer unattended. Invitations that grant power without control are rejected at creation. File transfer and power also require explicit local host policy. Permission and revocation checks happen on the host, not only in the GUI. Only one controller may be active.
4. **Desktop:** the host runs with the signed-in user's rights. It does not bypass UAC, screen lock, macOS privacy consent, disk encryption, or Wayland's permission system. Unsupported environments return capability errors rather than implying successful control.
5. **Local GUI:** Electron uses context isolation, sandboxing, disabled Node integration, denied web permissions, navigation restrictions, a strict content security policy, and an action-specific IPC bridge. Remote desktops arrive as H.264 video decoded by the browser engine's video decoder, or as PNG/JPEG images, never as executable HTML; stream records are size- and type-checked before decoding, and an access unit's keyframe flag must match its H.264 NAL slice types. File paths are selected through native dialogs opened by the main process; the renderer cannot supply a path, including the shared file-transfer folder.
6. **Lifecycle:** closing the window leaves the main process and host in the tray. The host monitors an owner-held stdin pipe and exits on EOF. The main process restarts failed hosts with backoff. Revocation/disconnect releases held input; independent input leases provide an additional bounded cleanup mechanism.

New desktop invitations start with viewing only. The host owner must explicitly grant keyboard/mouse, clipboard, file, or power access. A viewer must additionally choose **Take control** before sending input. Startup at sign-in is opt-in and does not provide access before sign-in.

Separate screen windows share one authenticated session. Each registered window is bound in the main process to a fixed session and monitor, and cannot manage devices, settings, invitations, or the parent session. Sender checks require the exact bundled page and its main frame. Frame geometry is stored per monitor; late responses from a replaced session are rejected before they can enable input. These windows share the same host desktop and do not provide per-monitor security isolation.

A paired host is not trusted to describe itself safely. Before the main process stores or shows a host's name, platform, grants, monitors, file listing or error text, it checks type and length and applies the host's own display-name rule: no control characters, line or paragraph separators, or Unicode format characters (bidi controls, zero-width space and others) except ZWNJ, ZWJ, LRM and RLM. A bad name keeps the previous or a neutral name, the platform is reduced to Windows, macOS, Linux or unknown, grants become plain booleans, and remote error text is cut to 500 characters with unsafe characters replaced. The same checks repair `connections.json` when it is loaded. If the window still meets a value it cannot draw, a recoverable error screen replaces the blank window.

Known limit: the GUI is loaded from `file://`. Its content security policy allows scripts only from `'self'`, but on a `file://` page `'self'` matches any local file, and Electron's `GrantFileProtocolExtraPrivileges` fuse stays on because the module bundle and its decoder worker do not load without it. Exploiting this would first need HTML injection into the GUI, and none is known. Serving the GUI from a custom protocol would remove both gaps; it is not done yet.

An explicit host stop rotates persisted automatic-resume authorization. The viewer treats stale renewal as terminal, clears access and queued input, and requires a new explicit connection. Normal host lifecycle recovery preserves authorization. This controls automatic recovery; use certificate revocation to prevent a paired device from explicitly connecting again. Internal resume epochs stay out of renderer-facing status. Pairing also refuses a saved host-ID collision with a different pinned certificate.

## Data protection

- Windows certificate bundles use current-user DPAPI. Restoring them under another account fails.
- macOS/Linux key bundles and state folders use user-only modes; integration with native secret stores is not yet implemented.
- The authenticated local main process can obtain the host private key for outgoing mTLS. It is never sent to the renderer, included in invitations, or logged. Moving all outgoing TLS into the host is a future hardening option.
- The fresh local control secret is passed to the owned child through its environment. Processes with same-user debugging/environment access are not contained by this design.
- An installed release refuses to start, before any window opens, when it is launched with Chromium debugging or sandbox-weakening switches such as `--remote-debugging-port`, `--remote-debugging-pipe`, `--inspect*`, `--no-sandbox`, `--disable-web-security` or `--js-flags`. Electron fuses already turn off `ELECTRON_RUN_AS_NODE`, `NODE_OPTIONS` and Node's inspector. A release also ignores the test variables `ORBIT_LOOPBACK_TEST`, `ORBIT_APP_DATA` and `ORBIT_CONTROL_PORT`, and its host child inherits no `ORBIT_*` variable (for example `ORBIT_REMOTE_PORT`). Development runs and the separately built, unfused end-to-end test package keep both. A refused launch shows an error dialog that names the switch before the app exits. One exception applies on Linux: an AppImage (the `APPIMAGE` variable is set) may start with `--no-sandbox`, because Ubuntu 24.04 and later restrict the unprivileged user namespaces Chromium's sandbox needs, so AppImages usually start only with that switch. Orbit then logs a warning on every launch and shows it once per profile; its windows run without the Chromium sandbox. A same-user process can set `APPIMAGE`, so on Linux this exception is available to it; Linux has no per-app privacy grant like macOS, and debugging switches stay refused on every platform. The Debian package installs Chromium's sandbox helper and is the better choice where it can be used. These checks raise the cost of misuse by a same-user process; they do not make such a process part of the trust boundary.
- Pairing invitations are bearer secrets and must be shared through a trusted channel. Verify the host with its owner; an invitation from an attacker identifies that attacker's host correctly.
- An experimental short pairing code (SRP-6a, F33) exists in the host but is off unless `ORBIT_EXPERIMENTAL_SHORT_CODE=1` is set. Do not enable it outside testing: enabling it by default is blocked on dependency hardening and review. See [PROTOCOL.md](docs/PROTOCOL.md#short-pairing-code-experimental-disabled-by-default).
- Logs record event types and device IDs, not invitation secrets, clipboard text, passwords, or screen contents. Remote clipboard reads and writes are audited with their byte count only. Refused pairing attempts, unknown or refused certificates and sources Tailscale does not verify are audited with the source address and a fixed reason, never the invitation. Repeated remote session and clipboard events are coalesced per device per minute, so a peer cannot flush the history. The host audit history is bounded; it is local and not tamper-evident.
- Certificate expiry currently requires deliberate identity rotation and re-pairing. Automatic rotation, key recovery, and signed update delivery are not implemented.

## Files and input

Remote file access is confined to one locally configured existing absolute directory. Root folders, directory traversal, invalid/reserved names, and symlink/reparse-point paths are rejected. Uploads use create-new semantics and bounded sizes; existing files are never remotely overwritten. On the viewing computer, remote file names that contain bidi, format or control characters, Windows-invalid characters, a trailing dot or space, or a reserved device name are left out of the listing and refused for download, so a name such as `invoice<U+202E>fdp.exe` cannot be shown or saved as `invoiceexe.pdf`. Received files still get Mark-of-the-Web on Windows and the quarantine attribute on macOS. The local directory should be private to the user: malicious local mutation of paths during file operations is outside the current threat model.

Remote keyboard/mouse support uses fixed typed events and static key mappings. There is no general command-execution API. Unsaved work can still be affected by an authorized controller. Lock/restart requests require explicit grants and opt-in policy; successful request acceptance is not proof of reboot recovery.

## Known limits

- **No local confirmation for remote lock or restart.** A device with the Control and Power grants, on a host with remote power turned on, can lock or restart the computer without any prompt, notification or cancel option on the host. The action is audited. Windows restarts after a 15-second grace period, macOS after one minute, and Linux may restart immediately; Orbit offers no way to cancel from the host. Leave remote power off unless you need it.
- **Control can lock or restart through the desktop.** See *Authorization* above: the Power grant does not stop a controlling device from using the desktop's own lock, restart or shut-down commands.
- **Any reachable tailnet node can attempt pairing.** See *Network* above: keep invitations private.

## Security review

An internal review in October 2026 covered the host, the desktop app and the supply chain. It found no Critical or High issues; the two Medium findings (both in the desktop app) are fixed, and the rest are Low or informational. [docs/SECURITY-REVIEW.md](docs/SECURITY-REVIEW.md) lists every finding with its status, the fix and its tests, the known limits, and how the result was verified. Releases up to and including `v0.1.0-preview.5` predate those fixes. The review was not an independent third-party audit.

## Required before a production release

- Independently review the host, Electron bridge, native adapters, pairing design, and dependencies.
- Test real two-computer sessions on each supported OS, keyboard layout, DPI scale, monitor topology, and network type, including relayed Tailscale paths.
- Implement and validate a separately privileged broker/session worker design before claiming Windows sign-in/UAC or system-boot operation.
- Validate macOS privacy permissions and pre-login network reachability on the exact supported hardware/OS versions; provide supported recovery paths.
- Implement Wayland through compositor-supported portals/EIS with real consent and persistence behavior.
- Ship signed Windows binaries, signed/notarized macOS applications, signed update metadata and rollback protections.
- Complete native secret storage, certificate rotation/recovery, dependency monitoring, and resource/load testing.
- Test lock, sign-out, restart, power failure, Tailscale disconnection, host/main crashes, missing displays, and revocation during active work.

## Reporting a vulnerability

Report security concerns privately through GitHub: open the public repository's **Security** tab and choose **Report a vulnerability** ([report a vulnerability](https://github.com/Optimizer077/orbit-remote/security/advisories/new)). Only the maintainer sees the report. Please do not open a public issue with details. Describe the affected version, the boundary involved, the impact, and a minimal sanitized reproduction, and leave out live invitations, private keys and desktop content.
